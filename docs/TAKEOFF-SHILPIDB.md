# Take-off in ShilpiDB: the contract between O-Draft and O-CoreOp

Written 2026-10-19 on the owner's instruction, revised the same day after the owner's answers (section 1). **Status: version 1, draft.** O-CoreOp's side is built and checked (section 9). O-Draft's side is not built; the instructions for it are in [HANDOFF-O-DRAFT-TAKEOFF.md](HANDOFF-O-DRAFT-TAKEOFF.md). Nothing was built on the first draft of this contract, so version 1 was revised in place instead of becoming version 2.

## 1. Decisions (owner, 2026-10-19)

1. **Drawing and PDF take-off is done in O-Draft** (repository `HolagundiWorks/O-DRAFT`, earlier AADT), not in O-CoreOp. O-CoreOp's PDF take-off panel is removed. **PDF underlay and calibration are O-Draft's to build.**
2. **O-Draft records the take-off in ShilpiDB; O-CoreOp reads it from there.** The bridge **file** (`hcw-aqc-bridge` v1, [bridge/](bridge/README.md)) stays as the offline path and as the format of each row.
3. **One shared ShilpiDB server.** O-Draft and O-CoreOp run **side by side**, so there is no file hand-over: both talk to the same running server, and a take-off is readable by O-CoreOp as soon as O-Draft has recorded it.
4. **A project can have several drawings.** Designed in section 5.
5. **The annotated drawing** (quantity lines, measurements, hatches) is **generated by O-Draft once the take-off is complete, as a PDF, and stored in O-CoreOp.** Designed in section 6.

## 2. What ShilpiDB is, for this purpose

A store of **records**: a `u64` id, a bounding box (two corners, `f64` each) and a payload of bytes. There are no tables or collections and no types; a record with an id that already exists is **replaced** (checked on the real server). `shilpid` serves one database file (`.vdb`) over TCP; `shilpi-http` is a JSON gateway in front of it: `GET /records` (ids and boxes), `GET /records/{id}` (box, `payloadText`, `payloadHex`), `PUT /records/{id}?minX=&minY=&maxX=&maxY=` (payload as the raw body), `DELETE /records/{id}`, `POST /save`. There are **no transactions** and no compare-and-set, which section 4 works around. Source: `HolagundiWorks/shilpidb`.

## 3. The shared server

| | |
|---|---|
| Server | `shilpid` on `127.0.0.1:7420`, autosave every few seconds |
| Gateway | `shilpi-http` on `127.0.0.1:7421`, backend `127.0.0.1:7420` |
| Data file | `%LocalAppData%\OSAS\takeoff\takeoff.vdb` |
| Who starts it | **Whichever app needs it first.** Check `GET /health` on 7421; if nothing answers, start both programs (they bind fixed ports, so a second starter fails harmlessly and uses the one that is up). O-CoreOp has a **Start the shared server** button. The OSAS launcher may start it at logon; that is the owner's call |
| Finding the programs | **Beside the app first** (engine bundle shipped with O-Draft / O-CoreOp), then `SHILPIDB_BIN`, then `%LocalAppData%\ShilpiDB\bin`, then `PATH`. ShilpiDB is not a separate product install for this path. |

It is **one database for all projects and drawings on the machine** (section 4 keeps them apart). Take-off data is derived (the drawing is the source), so losing the file loses nothing that cannot be recorded again; do not back it up as the system of record.

**Offline or archived take-offs:** O-CoreOp can also open a take-off `.vdb` file by itself, **reading the file directly, with no server** (`VdbFile`). A writer that has no shared server may save a `.vdb` with the same records. The file layout is the same whoever writes it: `"SHILPIDB"`, `u32` version, `u32` record count, then per record `u64` id, four `f64` box values and a `u32`-length payload, all little-endian; anything after the records (O-Draft appends a spatial-grid index) is ignored. **Two version numbers are in use:** `shilpid` writes and reads only **version 1**; O-Draft's own file writer writes **version 2**. O-CoreOp reads both. `shilpid` cannot open a version 2 file (`unsupported data file version 2`), so a file O-Draft saved cannot be served by `shilpid`; see section 10. A file that holds one drawing may use **slot 0** (ids `(kind << 56) | handle`, the original layout; O-Draft's file mode does); slot 0 must not be used on the shared server, where drawings would collide.

## 4. Records

Everything is millimetres (`"units": "mm"`; areas in m²) and every payload except an annotated-PDF chunk is **UTF-8 JSON, one object**.

### Id: kind, drawing slot, number

`id = (kind << 56) | (slot << 32) | n`: **kind** 8 bits, **slot** 24 bits (which drawing), **n** 32 bits.

| kind | Record | Payload |
|---|---|---|
| 1 | **Header**, one per drawing, `n = 0` | section 4.3 |
| 3 | Wall | the bridge file's `walls[]` row |
| 4 | Opening (door or window) | the `openings[]` row |
| 5 | Column | the `columns[]` row |
| 6 | Lintel | the `lintels[]` row |
| 7 | Room | the `rooms[]` row |
| 8 | Slab | the `slabs[]` row |
| 9 | Annotated-PDF chunk, `n` = chunk number from 0 | raw bytes of the PDF (section 6) |

Kinds 0, 2 and 10 to 255 are reserved. A reader skips an unknown kind and reports it, so a later version can add kinds.

### 4.1 The drawing slot

One database holds many drawings, and ids have no namespace, so each drawing owns a **slot**. It must be the same for the same drawing every time (re-recording replaces the same records) and must not collide with another drawing's.

- **Start from** `SlotFor(drawing_id)`: 32-bit FNV-1a of the UTF-8 bytes of the drawing id (offset basis 2166136261, prime 16777619, `h ^= byte; h *= prime` in 32-bit), then `slot = (h ^ (h >> 24)) & 0xFFFFFF`; if that is 0 use 1. **Test vectors:** `0b7d9c34-1e6f-4f0b-8a13-9b2c7d5e41aa` gives `6389047`; `6f1c1b0e-7a52-4d0a-9c1e-2d8a3f4b5c60` gives `15751439`.
- **On collision, probe:** read the header at `HeaderId(slot)`. If it exists and its `source.drawing_id` is a different drawing, try `slot + 1` (after `0xFFFFFF` comes `1`), until a free slot or this drawing's own header is found. Store the slot in the drawing (with its `drawing_id`) so later runs skip the probe.
- 24 bits gives 16.7 million slots; probing makes a collision a one-step detour, not a failure. Two writers claiming the same free slot within the same few milliseconds is theoretically possible (there is no compare-and-set) and is detected afterwards: after writing the header, read it back; if `drawing_id` is not yours, someone else won; take the next slot.
- `n` is the entity handle (hex handle as a number) when it fits in 32 bits, else the 32-bit FNV-1a of the handle string; for an item with no entity, a running number from 1 stored with the take-off. It must be the **same for the same item on every run.**

### 4.2 Item payload and bounding box

**The same fields as the bridge file row, unchanged** (see [bridge/hcw-aqc-bridge.schema.json](bridge/hcw-aqc-bridge.schema.json) and [bridge/fixtures](bridge/fixtures)): a wall is `{ "ref", "level", "length_mm", "height_mm", "thickness_mm", "layer" }`, an opening `{ "ref", "kind", "mark", "type", "level", "width_mm", "height_mm", "sill_mm", "wall_ref" }`, and so on. `ref` is the row's stable identity; O-CoreOp stores it as `source_ref`. `level` is the floor **name** from the header's `levels`.

The bounding box is the bounds of the measured geometry in the drawing's coordinates, in millimetres (zero-size at the origin when there is no geometry). O-CoreOp does not need it to import; it lets any client ask "what was measured in this window" and lets O-Draft select the item.

### 4.3 Header payload

```json
{
  "format": "hcw-takeoff-shilpi",
  "version": 1,
  "units": "mm",
  "state": "complete",
  "source": { "app": "O-Draft", "drawing": "small house.dxf", "drawing_id": "<GUID kept in the drawing>",
              "project_office_id": "<AORMS project office id, if the drawing is linked>",
              "project_ref": { "v": 1, "company_uuid": "<company file id>", "project_id": 0 },
              "exported": "2026-10-19T11:00:00Z", "revision_sha256": "<hash of the saved drawing>" },
  "project":  { "name": "", "client_name": "", "company_name": "", "location": "", "address": "" },
  "levels":   [ { "name": "Ground", "height_mm": 3150, "slab_thickness_mm": 150, "beam_depth_mm": 450 } ],
  "beam_depths_mm": [ 300, 450 ],
  "opening_schedule": [ { "mark": "D2", "kind": "Door", "width_mm": 900, "height_mm": 2100, "nos": 2 } ],
  "annotated_pdf": { "sha256": "<hex>", "bytes": 1234567, "chunks": 3, "pages": 1, "generated": "2026-10-19T12:00:00Z" }
}
```

Required: `format`, `version` 1, `units` `mm`, `source.drawing_id`. A reader refuses anything else and lists the drawing with the reason. `state` is `"recording"` or `"complete"` (missing means complete). `levels` are the floors **above the plinth** (`Lvl0` is O-CoreOp's and is never imported). `project_office_id` ties the drawing to a project (section 5). `annotated_pdf` is present only when a PDF is stored (section 6).

### 4.4 The writer's protocol (there are no transactions)

A reader can look at any moment, so the header is the **completion marker**:

1. Find the drawing's slot (4.1).
2. `PUT` the header with `"state": "recording"` and **without** `annotated_pdf`.
3. `PUT` every row. Existing ids are replaced.
4. `DELETE` the records of this slot (kinds 3 to 8) that are not in the new set, so the database equals the current take-off.
5. If an annotated PDF is being recorded: delete the old chunks, `PUT` the new ones (section 6).
6. `PUT` the header with `"state": "complete"` (and `annotated_pdf` if there is one), then `POST /save`.

A reader **refuses a drawing whose state is `recording`** and says so; it never imports half a take-off. If the writer dies between steps 2 and 6 the drawing stays `recording` until the next successful record; the reader shows that state with the header's `exported` time.

## 5. A project with several drawings

A project usually has several drawings (a floor each, sections, a site plan). Each is **its own take-off in its own slot**, with its own header, so they never overwrite each other and can be recorded at different times.

- **Which drawings belong to which project.** `source.project_office_id` is the AORMS project office id O-Draft already keeps with a linked drawing (`aorms.open`). O-CoreOp saves the same id on its project (File > Online projects > Link). The Take-off page lists **every** drawing in the database, puts the **linked project's drawings first** and marks them "this project", and marks others "another project". A drawing with no project id is listed unmarked; the user chooses.
- **Importing.** One drawing at a time: pick it, read it, review the preview, import. Rows are tagged `source = "hcwcad:<drawing_id>"` and `source_ref = <ref>`, so each drawing's rows are kept apart and each re-import updates only its own. Nothing is merged across drawings.
- **Levels** are matched **by name** across drawings, so two drawings that both name a floor `Ground` feed the same AQC level.
- **The rule that keeps quantities honest: one drawing per part of the building.** If two drawings both measure the same wall on the same floor (a plan and a detail sheet), O-CoreOp will import both and **double count**. It cannot know they overlap. O-CoreOp now **warns** (it does not block): when a drawing about to be imported adds rows on a floor and trade that another drawing already supplies, the preview lists "Check before importing" naming that drawing and floor, once per drawing and floor. The writer should still record only the drawing that is the measured source for a floor.
- **Removing a drawing's take-off** from the database is a delete in ShilpiDB by slot; rows already imported stay in O-CoreOp (it never deletes) and the next preview lists them as "no longer in the drawing".

## 6. The annotated drawing

When a take-off is **complete**, O-Draft generates an **annotated drawing PDF**: the drawing with the measured quantity lines, the measurements and the hatches, so a reader can see what was counted. It is **stored in O-CoreOp** with the project, and used in its reports.

- **O-Draft generates it** (a command it owns; the contract is only how it travels and what is checked).
- **Transport: ShilpiDB chunks.** Split the PDF into chunks of **at most 512 KiB** (the gateway returns payloads as hex, so each is read as up to 1 MiB of JSON); `PUT` chunk `i` as kind 9, `n = i`, raw bytes as the body, zero-size box. Total **at most 64 MiB**. Then the header's `annotated_pdf` carries the **SHA-256** (hex) of the whole PDF, its **byte count**, the **number of chunks**, the **page count** and the generation time. The PDF must be of the **same revision** the take-off was measured from (`revision_sha256`).
- **O-CoreOp fetches it on request** (button **Fetch annotated drawing** on the Take-off page), reassembles it, **checks** every chunk is present, the length, the SHA-256 and that it starts with `%PDF`, and refuses anything that fails. It stores the file beside the project (`<project name>.assets\annotated\<drawing>-<hash>.pdf`, or under `%LocalAppData%\O-CoreOp\annotated` until the project is saved) and records it in the project file (`annotated_drawings`: drawing id, file, SHA-256, generated, revision, fetched). A newer fetch for the same drawing replaces the older file.
- **Reading a take-off never downloads the PDF**: chunks are skipped by id.
- **Reports.** Every stored annotated PDF is embedded in the **project report** and the **estimate PDF** as an appendix: each page is rendered to an image (up to 8 pages per PDF; a note says if there are more) and drawn on its own report page, headed with the drawing name, the page number, when O-Draft recorded it and the first 8 characters of the drawing revision. A stored file that is missing or cannot be rendered is left out of the report (the Take-off page still lists it). Nothing is redrawn or re-measured in O-CoreOp. Code: `BBSApp/Services/StoredAnnotatedPdf.cs`.

## 7. Rules that do not change

These are the file importer's rules, because the records are turned into a bridge file and fed to it:

1. Imported rows get `source = "hcwcad:<drawing_id>"` and `source_ref = <ref>`. The prefix `hcwcad:` stays: it is stored in users' projects. A take-off imported from a file and the same drawing read from ShilpiDB **never duplicate each other** (tested).
2. Preview first, one undo step, nothing deleted; a row no longer in the take-off is listed as "no longer in the drawing" and kept.
3. A row the user edited in O-CoreOp after importing is flagged and left alone unless they choose to overwrite.
4. **Never send** plaster, painting, skirting, shuttering, rebar, PCC, earthwork, waterproofing or any rate or cost.
5. A column carries no height; O-CoreOp computes it from the level.
6. A wall of 120 mm or less is measured by O-CoreOp as its 110 mm wall.
7. **A wall's thickness:** `thickness_mm` when the row has it (a parametric wall always does); otherwise the layer says it (`MEASURE-FULLBRICK` 230 mm, `MEASURE-HALFBRICK` 115 mm, the 4.5 in wall, which is rule 6's 110 mm build); otherwise 230 mm, flagged "assumed, check it". An optional `material` is used when present (`brick.full`, `brick.half`, `block.concrete` as Cement Block with 200 mm assumed; `rcc` is skipped because an RCC wall is not masonry); `finish`, `component_type`, `schema_version` and provenance fields are ignored, because finishes are derived here.

## 8. How O-CoreOp reads it

File > Take-off from ShilpiDB (or **Take-off (O-Draft)** under Project):

1. The page reads the **shared server** (default `http://127.0.0.1:7421`) and **refreshes the drawing list every five seconds**, so a take-off appears when O-Draft finishes it. Or it opens a take-off `.vdb` file.
2. For each drawing it shows the name, state, number of rows, whether an annotated drawing is stored, and whether it belongs to the linked project. Listing downloads only the headers; counts come from the ids.
3. **Read take-off** downloads that drawing's rows (skipping other drawings and chunks), turns them into a bridge file, validates it and shows the import preview. Records it cannot use are counted and named.
4. **Fetch annotated drawing** downloads, verifies and stores the PDF (section 6).

Code: `BBSDesktop/AQC.CadImport/ShilpiTakeoff.cs` (contract, reader, gateway client; platform-neutral), `BBSDesktop/BBSApp/Services/Shilpi/ShilpiTakeoffService.cs` (servers, listing, reading), `BBSDesktop/BBSApp/Services/StoredAnnotatedDrawing.cs` (storing the PDF), `BBSDesktop/BBSApp/Views/TakeoffPage.cs`.

## 10. Reading what O-Draft actually wrote (2026-10-19)

O-Draft's `takeoff.record` was run (its own test, against a real `shilpid`) and the database it left was read with this reader. The records are kept as a regression fixture, `BBSDesktop/AQC.CadImport.Tests/fixtures/odraft-takeoff-records.json`, and `ODraftOutputTests` (10 tests) reads them.

**Agrees with the contract (checked):** the header is `complete`; the id layout and kinds are as written here; the slot O-Draft chose for its drawing id equals the slot this reader computes (two independent implementations of `SlotFor`); one header per drawing; every payload parses; nothing was skipped; the take-off imports and importing it again changes nothing.

**Differences, and what O-CoreOp does about each** (the first three also go to O-Draft as requests, section 8 of its hand-off):

| What O-Draft writes | Effect | What O-CoreOp now does |
|---|---|---|
| A room row has `area_m2` and `size` text but **no `level`, no `length_mm`, no `breadth_mm`** | the flooring row was skipped ("level '' is not in the file's levels") | A row with no level goes to the file's floor when the file has exactly one (several floors: skipped, with that reason). Length and breadth come from the record's **box** (the room's drawn outline, millimetres) when the box agrees with `area_m2` to 2%; if not (an L-shaped room) the area is kept exact, the box's shorter side is the breadth, and the row is flagged "approximate" |
| Openings carry **no `wall_ref`** | they would be imported without a wall and not deduct | The opening is placed in the nearest wall **on the same level whose box, widened by 150 mm, meets the opening's box**; the preview flags it "wall chosen by position; check it". No wall within reach: left without a wall and flagged as before |
| Walls carry **no `thickness_mm`** (only the layer, for example `MEASURE-FULLBRICK`) | the importer assumed 230 mm silently | Still 230 mm, but the preview now says "no wall thickness; 230 mm assumed, check it" |
| `opening_schedule` has `"kind": "Ventilator"` | an opening of that kind would have become a door | A ventilator is a window (mark V1) |
| Header `levels` rows also carry `ceiling_mm` and `lintel_bottom_mm`; `source.drawing` is empty for an unsaved drawing; `project_office_id` is absent for an unlinked drawing | none | Accepted; the Take-off page shows the slot number when the name is empty |

The Take-off page's status line says how many values were worked out from positions or outlines. **Not checked:** the annotated PDF O-Draft records (its tests use a stand-in plotter; this reader's chunk path was checked with its own writer against a real server, not with O-Draft's), a database with several drawings written by O-Draft, `project_office_id`, and a take-off with more than one floor.

### 10.1 Parametric walls and the file format (2026-10-19, second read)

O-Draft added **parametric walls** (hand-off: [HANDOFF-O-COREOP-PARAMETRIC-TAKEOFF.md](HANDOFF-O-COREOP-PARAMETRIC-TAKEOFF.md)). Its engine was built from a copy, a 5 m wall made with `param.wall.new` and `param.commit`, recorded with `takeoff.record { path }`, and the file read here (`fixtures/odraft-parametric.takeoff.vdb`, test `VdbFileTests`).

- **The wall row** is `{ ref "PW-wall-1", level, length_mm, height_mm, thickness_mm 230.0, layer "A-WALL" }` with the face lines' box. It reads and imports as one masonry row (230 mm, 5000 by 3000) with no warning. A `PW-` wall and a brick wall (`W`+handle, layer `MEASURE-FULLBRICK`, no thickness) in one drawing each keep their own thickness. `ParametricWallTests`: 11.
- **Brick rows have no `thickness_mm`**, so rule 7 of section 7 takes it from the layer.
- **Mismatch: the file is not readable by `shilpid`.** O-Draft's file writer writes format version 2 and the installed `shilpid` 0.2.0 accepts only version 1 (`unsupported data file version 2`). The layout is identical. O-CoreOp reads both versions itself. O-Draft's file mode also writes slot 0 (see section 3). Both are reported to O-Draft in its hand-off, section 9.
- **Checked in the real app** (`BBSDesktop/tests/e2e/uia-vdbfile.ps1`, 9 checks): choose O-Draft's file in the file dialog; the drawing is listed (`drawing 0 · complete · 1 rows`), reads, and previews "1 to add".

## Versioning

A change to a field, a kind number, the id layout or a unit is a new `version`, decided by the owner, in this file and in O-Draft together. Adding a kind or an optional field is not.
